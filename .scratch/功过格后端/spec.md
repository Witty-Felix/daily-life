# 功过格后端云端存储

## Problem Statement

当前应用中的功过格虽然已经具备本地/服务端抽象、HTTP API、账户认证和 SQLite 适配器，但还没有形成一份可直接实施和上线的统一规范。用户拥有一台阿里云 Linux 服务器、宝塔面板和一个正在进行备案的域名，希望把功过格数据稳定保存到服务器，并在刷新页面、更换浏览器或更换设备后继续使用。

课间休息与功过格是两个独立的一级模块。课间休息目前属于本地功能，不应因为功过格云端化而被顺带上传。贪吃蛇也不需要保存完整游戏状态；本规范只定义保存每个账户个人最高分的能力，不构建排行榜或竞争系统。

## Solution

将功过格部署为自托管的单机后端系统：浏览器通过正式域名的 HTTPS 访问 Nginx，Nginx 将功过格 API 反向代理到本机 Node.js 服务，Node.js 使用本机持久磁盘上的 SQLite 保存功过记录、认证数据和账户私有的贪吃蛇个人最高分。

复用现有的功过格领域模型、HTTP API 契约、Node.js 服务、SQLite 适配器和账户认证基础。后端按账户隔离数据，并继续支持功过记录、统计、历史修正、删除/恢复、导出和必要的迁移能力。贪吃蛇仅提交分数，服务端只在新分数高于个人已有最高分时更新；课间休息继续使用浏览器本地存储，不进入云端 API、SQLite、云端导出或服务器备份。

部署采用版本化发布、独立数据库目录、低权限运行用户、Nginx 反向代理、systemd 或等效进程托管、定期 SQLite 一致性备份和可验证恢复。备案完成前只进行本地、服务器本机、SSH 隧道或受控网络验收；正式域名解析、HTTPS 切换和正式 WebAuthn 验收在备案及接入条件满足后进行。

## User Stories

1. 作为功过格用户，我想在正式域名下访问功过格，以便不依赖本地开发环境。
2. 作为功过格用户，我想登录自己的账户，以便访问属于自己的记录。
3. 作为功过格用户，我想在刷新页面后保持登录状态，以便不中断自省流程。
4. 作为功过格用户，我想在另一台设备登录同一账户，以便继续查看功过记录。
5. 作为功过格用户，我想使用恢复码登录，以便在没有已注册通行密钥时进入账户。
6. 作为功过格用户，我想使用通行密钥登录，以便使用更安全和便捷的认证方式。
7. 作为功过格用户，我想注册新的通行密钥，以便在更多可信设备上登录。
8. 作为功过格用户，我想查看已登录设备，以便了解账户访问情况。
9. 作为功过格用户，我想撤销某个设备的会话，以便阻止该设备继续访问账户。
10. 作为功过格用户，我想退出其他设备，以便在怀疑账号被使用时快速收回访问权。
11. 作为功过格用户，我想在执行永久删除等敏感操作前重新认证，以便降低误操作和会话被盗后的风险。
12. 作为功过格用户，我想轮换恢复凭据，以便旧恢复凭据不再长期有效。
13. 作为功过格用户，我想删除账户，以便控制自己的账户和数据生命周期。
14. 作为功过格用户，我想记录一件善行，以便保存当天完成的具体正向行为。
15. 作为功过格用户，我想记录一件过失，以便保存当天需要反省或改进的具体行为。
16. 作为功过格用户，我想让善行自动按产品规则计为 `+1`，以便记录规则稳定一致。
17. 作为功过格用户，我想让过失自动按产品规则计为 `-2`，以便记录规则稳定一致。
18. 作为功过格用户，我想填写具体行为描述，以便记录不会退化为空分数。
19. 作为功过格用户，我想填写可选的反思或修复行动，以便为过失留下下一步改进方向。
20. 作为功过格用户，我想看到今天的善行数量，以便快速了解当天的正向记录。
21. 作为功过格用户，我想看到今天的过失数量，以便快速了解当天需要反省的记录。
22. 作为功过格用户，我想看到今天的净分，以便快速获得当天的概览。
23. 作为功过格用户，我想查看最近日期的功过记录，以便进行连续的日常自省。
24. 作为功过格用户，我想按日期查看历史记录，以便回顾过去的行为。
25. 作为功过格用户，我想按日期范围查看统计，以便观察一段时间的记录变化。
26. 作为功过格用户，我想修改当天记录，以便纠正刚刚输入的内容。
27. 作为功过格用户，我想对历史记录追加修正，以便保留可追溯的更正过程。
28. 作为功过格用户，我想看到历史修正信息，以便知道记录如何发生变化。
29. 作为功过格用户，我想删除当天记录，以便清理误记内容。
30. 作为功过格用户，我想在恢复期内恢复误删记录，以便避免误删造成的数据损失。
31. 作为功过格用户，我想永久删除记录前进行明确确认和重新认证，以便不可逆操作不会被误触。
32. 作为功过格用户，我想导出自己的功过数据，以便备份或迁移。
33. 作为功过格用户，我想导入旧的功过数据前先预览结果，以便在提交前发现错误。
34. 作为功过格用户，我想重复提交同一个迁移批次不会产生重复记录，以便网络重试不会破坏数据。
35. 作为功过格用户，我想在多个设备同时修改记录时得到冲突提示，以便不会静默覆盖另一台设备的修改。
36. 作为功过格用户，我想让我的功过记录只对我的账户可见，以便保护个人隐私。
37. 作为功过格用户，我想保存贪吃蛇个人最高分，以便知道自己曾经达到的最好成绩。
38. 作为功过格用户，我想在新成绩更高时更新个人最高分，以便最高分始终代表最佳成绩。
39. 作为功过格用户，我想在新成绩更低时保留原最高分，以便历史最佳成绩不会被覆盖。
40. 作为功过格用户，我想让贪吃蛇最高分只属于我的账户，以便其他账户无法读取或修改。
41. 作为功过格用户，我想让贪吃蛇只提交最终分数，而不是整个游戏过程，以便减少隐私和实现复杂度。
42. 作为功过格用户，我不想看到排行榜或公开比较，以便功过格和贪吃蛇保持个人工具属性。
43. 作为课间休息用户，我想继续在浏览器本地使用课间功能，以便本次云端化不会扩大功能范围。
44. 作为课间休息用户，我不希望课间状态、历史和设置被上传，以便保持既定的本地隐私边界。
45. 作为课间休息用户，我接受更换设备或清除浏览器数据后课间本地记录不自动恢复，因为本规范不包含课间云同步。
46. 作为部署人员，我想把数据库放在静态网站目录之外，以便用户不能通过 URL 下载数据库。
47. 作为部署人员，我想让 Node 服务只通过本机端口提供服务，以便公网请求必须经过 HTTPS 反向代理。
48. 作为部署人员，我想让公网只开放必要的 Web 端口，以便减少服务器攻击面。
49. 作为部署人员，我想让后端以低权限系统用户运行，以便限制服务被入侵后的影响范围。
50. 作为部署人员，我想保存多个版本的应用发布物，以便出现问题时可以快速回滚代码。
51. 作为部署人员，我想让数据库和应用发布物分离，以便代码回滚不会意外覆盖用户数据。
52. 作为部署人员，我想定期生成经过完整性检查的 SQLite 备份，以便发现数据库损坏而不是等到恢复时才发现。
53. 作为部署人员，我想在隔离环境演练备份恢复，以便确认备份确实能够恢复功过记录。
54. 作为部署人员，我想在备案完成前使用受控方式验收服务，以便不提前公开切换未备案正式域名。
55. 作为部署人员，我想在正式域名启用后验证 HTTPS 和证书续期，以便用户始终通过安全连接访问。
56. 作为部署人员，我想让前端、API 和 WebAuthn 使用同一个规范域名，以便通行密钥注册和登录不会因来源不一致失败。
57. 作为部署人员，我想在发布前检查账户隔离、认证、数据读写、备份和回滚，以便上线不是只验证首页能打开。
58. 作为维护人员，我想知道服务无法启动、数据库损坏或证书异常时的处理步骤，以便可以有序恢复服务。

## Implementation Decisions

- 采用单机自托管架构：浏览器、Nginx、Node.js API、SQLite，不引入微服务、消息队列或复杂云数据库。
- 正式后端提供方采用阿里云服务器上的 Node.js + SQLite；现有 Supabase 实现暂不作为正式生产主线。
- 复用现有功过格领域模型、`VirtueApi`、HTTP 客户端契约、Node HTTP 路由、SQLite 适配器和自托管认证服务。
- 功过记录、认证数据和贪吃蛇个人最高分必须按照账户隔离；任何读写都不能通过客户端提交的任意账户标识绕过服务端身份。
- 功过格继续支持首页聚合、记录查询、日期范围统计、新增、当天修改、历史修正、软删除、恢复、永久删除、导出和迁移预览/提交。
- 当天记录可以直接修改；历史记录只能追加可追溯修正，不允许无痕覆盖原始历史。
- 永久删除账户、永久删除记录、恢复凭据轮换等敏感操作要求短期、一次性、用途绑定的重新认证证明。
- 认证系统继续使用邀请制账户；恢复码和通行密钥属于账户认证边界，不与功过记录混成前端可控字段。
- 生产环境必须增加或验证认证接口的登录失败限流、请求体限制、安全审计和统一错误响应，避免恢复码枚举、暴力尝试和敏感信息泄露。
- 会话令牌不得写入日志、备份、导出或普通错误信息。生产实施阶段应优先评估 HttpOnly、Secure、SameSite Cookie；若暂时保留 Bearer/localStorage，必须配合严格 CSP、依赖审查和明确的风险接受记录。
- SQLite 使用单进程、单共享连接的部署拓扑；不允许多个 Node 实例同时写同一个数据库文件。
- SQLite 生产配置必须验证 WAL、busy timeout、事务边界和锁冲突处理；写入失败时返回稳定错误，不静默丢失数据。
- 数据库结构从隐式运行时建表逐步升级为有序、可审计、可回滚的 schema migration，并保留版本记录。
- 功过记录至少需要账户、记录 ID、自然日、类型、描述、反思、版本、删除状态、创建/更新时间和修正信息；永久删除墓碑用于防止旧备份重新导入已删除记录。
- 迁移批次必须按账户和批次 ID 幂等；预览、提交和结果保存的事务语义必须明确，不能出现记录已写入但批次结果未保存的部分提交。
- 贪吃蛇只新增账户私有的个人最高分存储能力，不保存完整游戏状态、不保存课间 ID、不保存每日局数、不提供排行榜或跨账户查询。
- 个人最高分更新必须是服务端原子比较更新：只有提交分数高于已有最高分时才更新；分数必须是非负整数。由于分数来自浏览器，该数据只作为个人记录，不宣称为可信竞技成绩。
- 课间休息继续使用浏览器本地存储；其状态、历史、活动完成、动画设置和局数不进入功过格 API、SQLite、云端导出、迁移或服务器备份。
- 前端在构建时通过云端 API 配置启用功过格云端入口；课间入口不因该配置而改变存储边界。
- 正式部署使用版本化 release 和 `current` 指向当前版本；数据库文件位于独立数据目录，环境配置文件位于服务器受保护路径，不提交真实凭据。
- Node 服务由 systemd 或等效进程管理器托管；静态前端由 Nginx 提供，功过格 API 仅代理到本机 Node 端口。
- 公网只开放 80/443；Node API 端口不得被安全组或系统防火墙暴露；SSH 与宝塔面板应限制到管理员网络。
- 备案完成前只允许本地、服务器本机、SSH 隧道或受控网络验收，不把未备案正式域名公开解析到中国大陆生产实例。
- 正式上线时使用唯一规范域名；前端 API 地址、WebAuthn RP ID、WebAuthn Origin、Nginx server name 和 HTTPS 证书覆盖范围必须一致。
- 备份使用 SQLite 的一致性 backup 机制，并对备份执行完整性检查和哈希校验；不能把正在写入的数据库文件简单复制视为已验证备份。
- 备份恢复必须先隔离当前数据库，再校验备份、恢复到独立或维护环境、验证 API 读取和导出，最后才替换生产文件。
- 代码回滚优先通过切换到上一稳定 release 完成，不以回滚代码为理由自动回滚数据库；数据恢复属于单独的、经过审批的恢复流程。
- 生产切换的最高测试接缝为 HTTP API 契约和真实浏览器端到端流程：在 API 层验证账户隔离、记录行为、最高分幂等更新和错误语义，在浏览器层验证登录、导航、刷新恢复、功过操作和课间本地边界。尽量复用现有单元测试、服务器测试、SQLite 测试和 Playwright 测试，不为内部实现细节新增测试。
- 方案不包含 Supabase 的直接上线修复；若未来重新选择 Supabase，必须单独补充账户表、统一身份映射、原子迁移提交和端到端认证验收。

## Testing Decisions

- 测试只验证外部行为、数据隔离、错误语义和可恢复性，不锁定内部函数调用顺序或具体 SQLite 实现细节。
- 复用现有领域测试验证善行/过失分值、日期校验、净分统计和贪吃蛇局内规则。
- 扩展 API 契约测试，验证 Node.js + SQLite 后端对功过格客户端所需操作的一致响应，包括成功、未认证、无权限、参数错误、冲突、已删除和服务不可用等情况。
- 扩展 SQLite 行为测试，验证账户隔离、版本冲突、当天修改、历史修正、软删除/恢复、永久删除墓碑、迁移预览和批次幂等。
- 增加认证行为测试，验证邀请账户、恢复码一次性使用、Passkey challenge 生命周期、会话撤销、退出其他设备、重新认证和账户删除；测试中不输出真实凭据。
- 增加贪吃蛇个人最高分测试，验证首次保存、较高分更新、较低分不覆盖、重复提交幂等、非负整数校验和账户隔离；验证不存在排行榜或跨账户查询能力。
- 增加服务器边界测试，验证认证失败的 HTTP 状态、请求体限制、错误响应不泄露令牌/恢复码、静态前端与 API 路由边界，以及 Node 仅接受预期代理访问的部署配置。
- 增加数据库迁移测试，使用空数据库、当前数据库和旧版本数据库验证迁移顺序、重复执行安全、失败回滚和 schema 版本记录。
- 增加并发/锁行为测试，至少覆盖两个请求同时写入、版本冲突、busy timeout 和可重试错误；不以高并发性能指标替代数据正确性验证。
- 增加备份恢复验收：生成 SQLite 一致性备份，执行完整性检查，恢复到隔离数据库，比较账户数量、记录数量、善行/过失数量、净分、修正链、永久删除清单和个人最高分。
- 增加浏览器端到端验收：正式或等价 HTTPS 环境下完成登录、功过记录、刷新恢复、跨设备语义、最高分显示/更新和错误提示；确认课间休息仍只读写本地存储。
- 备案前的验收不得被解释为正式域名 WebAuthn 验收；真实 WebAuthn 必须在最终规范域名、HTTPS、RP ID 和 Origin 完整一致后重新验证。
- 发布放行前至少通过类型检查、单元/集成测试、构建测试和关键端到端测试；真实服务器上线前还必须完成 Nginx 配置检查、服务启动检查、端口暴露检查、备份恢复演练和代码回滚演练。

## Out of Scope

- 课间休息云端同步、跨设备恢复、课间历史云端备份和课间活动完成上传。
- 贪吃蛇完整游戏状态、录像、操作轨迹、每日局数、课间关联数据和云端实时对战。
- 公开排行榜、全站最高分、好友排名、昵称排名和任何竞争化激励。
- 多租户组织管理、团队账户、管理员后台和公共分享。
- 复杂云数据库、微服务、消息队列、对象存储作为主数据库和跨地域高可用集群。
- 直接把当前 Supabase 迁移当作已验证生产方案。
- 在未确认备案、域名接入、证书和服务器资格前承诺正式公网可用。
- 把客户端提交的贪吃蛇分数当作防作弊、竞赛或财务级可信数据。
- 自动索取、保存或提交用户的阿里云、宝塔、SSH、DNS、证书、恢复码、API 密钥或其他敏感凭据。

## Further Notes

- 本规范基于截至 **2026 年 9 月 13 日** 已完成的代码审查和部署研究；当前研究验证了仓库中的类型检查与 14 个测试文件、77 个测试，但没有代替真实阿里云部署、真实域名 HTTPS、真实 WebAuthn、Supabase 端到端验证或多进程 SQLite 压测。
- 用户提供的阿里云截图和备案进度截图属于部署背景信息，不构成功能需求或安全凭据授权。
- 当前推荐的生产主线是“阿里云单机 + Node.js + SQLite + Nginx”，但实现前仍应先确认服务器地域、操作系统、Node/Nginx/宝塔版本、域名规范入口和备案/接入状态。
- 若实现阶段发现认证令牌、迁移原子性、SQLite 并发或备案规则存在不能安全假设的差异，应暂停对应上线步骤，记录差异并补充决策，而不是以默认值继续发布。
- 本规范的完成标准是：功过格能够通过正式 HTTPS 后端可靠保存和恢复，贪吃蛇能够保存账户私有个人最高分，课间休息仍保持本地化，且关键数据隔离、备份、恢复和回滚验收全部通过。
